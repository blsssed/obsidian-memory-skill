# 提取规则（extraction-rules）

`/save-memory` 第 1 步使用。目标：从对话中挑出**半年后回看仍然有用**的知识，宁可漏记不可记噪音。

## 硬性总则（优先级最高，违反任何一条即放弃该条提取）

1. **白名单是封闭世界**：只有命中下方五类之一才可提取。任何未列入的类目——"用户在备考""有教学价值""用户似乎感兴趣""这次对话很重要"等情境理由——**不构成提取依据**。
2. **模型不得创设豁免**。唯一合法的白名单外写入：用户明确说"把这条存下来"，此时 frontmatter 标注 `source: user-requested`。
3. **标准文档知识默认排除**：参数定义、语法、算法原理等半分钟能查到的内容不记。例外：对话产出了**非默认的实践选择及其理由**（如"Agent 场景 temp=0 因为要确定性"）——只记这个增量。
4. **增量原则**：vault 已有笔记（含用户自己的笔记）已覆盖的内容，只提取增量部分；无增量则不提取。

## 提取审计表（写入前必须先输出给用户）

| 候选知识 | 命中类目 | 判定理由（一句话） |
|---|---|---|
| … | #1 踩坑与解法 | … |
| … | 无 | 丢弃 |

- 类目列必须写编号，**"无"的条目直接丢弃**，不进入写入流程
- 用户对审计表提出异议时，按用户意见调整（这是用户的显式指令）

## 五类白名单（命中任意一类即提取）

### 1. 踩坑与解法
报错信息 → 根因 → 修复方式的完整配对。判定：这段经历下次遇到同样报错能直接救我。
- ✅ 例："`openspec init` 报找不到命令，根因是全局 npm 路径没进 PATH，修复：D:\develop\nodeJs 加入 PATH"
- ❌ 例：一次性的业务 bug（改完就没了，无复用价值）

### 2. 可复用素材的工程经验
判定：存在一段可跨项目复用的命令/配置/代码片段，**且对话中产生了关于它的经验**（适用条件、坑、选型理由）。
- 记录的是"**经验 + 指向片段的链接**"：超过 10 行的代码/配置一律存入 `AI记忆/snippets/`（模板见 note-template.md），笔记正文只留链接和一两行说明
- ✅ 例："tenacity 重试会与 SDK 自带 max_retries 叠加导致等待翻倍，手写前先查 SDK" + `[[tenacity重试模板]]`
- ❌ 例：单纯一段正则、一个配置块——无经验附着时，**最多存 snippet 文件本身，不建经验笔记**

### 3. 关键决策及其理由
判定：未来有人问"为什么这么做"时，这段理由能避免重新踩坑。
- ✅ 例："选 skill 而不是 MCP server，因为 MCP 拿不到对话历史"
- ❌ 例：变量命名偏好

### 4. 被推翻的认知
判定：对话前后认知发生了修正。
- ✅ 例："原以为 Obsidian 图谱是独立数据库，实际是链接的实时投影"
- 记录格式：原认知 → 实际情况 → 证据

### 5. 项目事实
判定：不看代码无法得知、但影响后续工作的环境/架构事实。
- ✅ 例："vault 在 Documents/Obsidian Vault，约百篇笔记、无 frontmatter"
- ❌ 例：能从 README、代码结构直接读出的信息

## 排除清单（命中即丢弃）

- 闲聊、寒暄、与知识无关的流程性对话
- 可从代码、git 历史、项目文档推导的内容
- 密码、API key、token、内网地址等**敏感信息（无例外）**
- 已有笔记完全覆盖的重复知识（交给合并规则处理，不重复记录）
- **标准文档知识**（见总则 3）
- **情境性理由**（见总则 1）——"用户在备考"不是类目

## 数量约束

- 单次对话提取 **1~6 条**知识；超出时按复用价值排序取前 6
- 每条知识在笔记正文中的呈现不超过 10 行（大段素材已外置到 snippets/）
- 拿不准某条该不该记时，**默认不记**
